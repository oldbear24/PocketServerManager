# Data model

PocketBase collections, created by Go migrations in [`migrations/`](../migrations/). The collections of M0 to M2, and those of the backups of M4 up to per-database backups and restore tests (#53), exist and are described as implemented; the others are reserved and land with their features. `internal/schema` lists the names, the encrypted fields and what the audit covers, and this document is updated together with the migrations.

Conventions:

- Every collection has PocketBase's `id`, `created` and `updated`.
- Fields marked 🔒 are text fields, hidden from the API, sealed with the master key before they are stored, and never written to the audit log.
- Agents never use the REST API; everything agents report arrives over gRPC and is written by the panel.

## Identity and access

| Collection | Purpose | Key fields |
|---|---|---|
| `users` (auth, built-in) | People using the panel. There is no public sign-up: the first account comes from the setup link in the panel's log, later ones from admins | `role` (admin / operator / viewer), MFA settings |
| `api_tokens` | Scoped tokens for automation (CI) | `name`, `token_hash`, `scopes[]`, `expires_at`, `last_used_at`, `last_used_ip`, `created_by`, `revoked_at` |
| `enrollment_tokens` | One-time tokens for connecting servers | `token_hash` (hidden), `hint`, `name`, `roles[]`, `expires_at`, `used_at`, `created_by`, `host` |
| `audit_log` | Append-only change and security log | `seq`, `at`, `category` (change / security / system), `action` (create / update / delete / revert / sign_in / checkpoint / …), `actor_kind` (user / token / superuser / system / anonymous), `actor`, `actor_label`, `source` (ui / api / pb_admin / migration / scheduler / agent / panel), `ip`, `user_agent`, `collection`, `record_id`, `record_label`, `host`, `changes` (json: field → from / to, secrets only as “changed”), `snapshot` (json: the last state on delete, details of security events), `command`, `revision`, `note`, `prev_hash`, `hash` |

`audit_log` has no create, update or delete API rules; entries are written only by the audit writer, and hooks reject every other write, for superusers too (retention excepted, see [Change audit](architecture.md#change-audit)). Admins read everything; operators only see the category `change`. The head of the chain, sealed with a key derived from the master key, is kept in the plain table `_pc_audit_head` (one row: `seq`, `hash`, `mac`, the last sealed `sealed_seq`, `sealed_hash`, `sealed_mac`, and `keyless`, the sealed ranges of entries written without the master key), created with the first entry, which the API and the dashboard do not see.

API rules in short: viewers read, operators manage workloads, admins do everything. Collections the panel itself maintains (`containers`, `events`, `stack_revisions` and others) cannot be written through the API at all.

Live diagnostics (connection stats, message trace, queue latencies) are kept in memory by the diagnostics plugin and are not stored in collections.

## Databases

| Collection | Purpose | Key fields |
|---|---|---|
| `db_servers` | A MariaDB or PostgreSQL server on a host: `shared`, which PocketCloud runs as a stack of its own, or `dedicated`, a database container inside an application's stack that someone linked | `host`, `name`, `engine` (mariadb / postgres), `version` (as the server reports it), `kind` (shared / dedicated), `image`, `container_ref` (container name), `service` (Compose service), `stack` (the server's own stack, or the application's for a dedicated server), `volume`, `port`, `admin_user`, `admin_password` 🔒, `max_connections`, `connections`, `extensions[]`, `status` (creating / ready / failed), `size_bytes`, `stats_at`, `last_error` |
| `databases` | One database on a server | `server`, `name`, `owner_kind` (none / stack / site), `stack`, `site` (a PHP site's, which keeps it when the site is removed), `size_bytes`, `connections`, `temporary_until` (set on PocketCloud's temporary databases, #53, whose owner is `none`: a restore test's copy `pc_rt_<check id>`, a restore's scratch copy `pc_rs_<restore id>`, the data a PostgreSQL restore in place replaced `pc_old_<restore id>`, and a name of that form a server reports without a record; the panel drops the database at that time. No other database may have such a name), `status` (creating / ready / failed / dropping), `last_error` |
| `db_users` | Database users created by PocketCloud, one per database, and the users of databases that moved from an application's own server | `server`, `name`, `password` 🔒, `pending_password` 🔒 (a new password until the server has taken it), `databases[]`, `secret_name` (`db/<database>`), `rotated_at`, `app_password` (the application keeps this password in its own settings, so the panel does not rotate it) |
| `db_networks` | A server on the internal network of an application | `server`, `name` (`pcdb-<stack>`: one network per application, which each of its servers joins), `stack`, `site` (`pcdb-site.<site>` for a PHP site's, removed with the site), `aliases[]` (the names of the application's own database service whose data moved to this server, which the server answers to on this network) |
| `db_dumps` | SQL exports, the final dumps of dropped databases and the copies of moved ones (admins only) | `server`, `database_name`, `kind` (export / final / move), `command`, `requested_by`, `file` (gzip, at most 1 GiB), `size_bytes`, `expires_at` (exports 7 days, final dumps and moves 30) |
| `db_moves` | A move of databases into a shared server: all of a stack's own server, or one database of a shared server for a newer version | `host`, `stack`, `target`, `target_name`, the source as it was (`source_name`, `source_kind`, `source_container`, `source_service`, `source_volume`, `source_version`), `databases[]` (name and user), `secrets` 🔒 (the passwords the databases keep, until the command is delivered), `status` (moving / moved / failed), `command`, `requested_by`, `error`, `moved_at`, `remove_after` (when the old container goes, 7 days on), `removed_at` |

The REST API only reads these collections (a move without its secrets), except that admins may delete a dump: the panel's own routes under `/api/pc/` write them, generate the passwords and queue the commands. A dedicated server's databases are listed from its statistics, without users, because they belong to their stack. A temporary database's record is made in the transaction of the command that makes the database and deleted once the database is dropped; operators drop one sooner through `DELETE /api/pc/databases/{id}`, and the Databases page leaves temporary databases out of its counts (#53). Sizes and connection counts come from `db.stats`: once an hour, and when an operator opens a server on the Databases page or refreshes it, at most once a minute per server. There is no history of them.

| `backup_checks` | A check of a target's repository (#31): `restic check` of one group of its data packs, first without a lock and, when it finds errors, again under the exclusive lock; and a restore test of a database's job (#53): its newest dump restored into a temporary database on its server as the database's own user, and its tables counted | `target`, `host` (the target's server, whose agent checks it; for a restore test the job's server, whose agent restores), `kind` (integrity / restore_test), `trigger` (schedule / manual / retry), `status` (queued / running / ok: no error, or none the second pass confirmed / failed: errors confirmed / suspect: errors the second pass could not confirm / error: it did not complete / skipped: it did not start / cancelled), `scheduled_at` (the slot of the schedule, on a scheduled check's first attempt only: one per kind, target, job and slot), `started_at`, `finished_at`, `duration_ms`, `subset` (n/t; empty for the structure only), `packs_read`, `packs_total`, `confirmed`, `unconfirmed`, `errors` (json: what restic found, at most 20), `errors_more`, `repair` (json: restic's advice), `notes` (json: what is no error), `lock` (json: the lock that kept the second pass out), `error`, `log` (the end of the job's output, secrets hidden), `command`, `attempt`, `retry_of` (one retry per check), `retry_at`; for a restore test (#53): `job` (removed with it), `database_name`, `snapshot_id`, `temporary` (`pc_rt_<id>`, the copy), `tables_expected` (in the dump), `tables_restored`, `dump_bytes`, `failure` (damaged / incomplete / restore / tables: the backup could not be restored, and the test failed / unreachable / repository / locked / space / container / sign_in / interrupted: the test could not tell). Viewers read it; only the panel writes it, never audited; removed after 180 days, except the newest check, and the newest that completed (ok or failed), of each target and kind, and of each job for restore tests; removed with its target or server |
| `recovery_kits` | The recovery kits the panel sealed, and who checked them (#32): never a kit, its passphrase or the key, only what says whether a kit is current | `kit_id` (KIT-XXXX-XXXX, unique), `key_id` (the id of the master key it holds), `digests` (json: one per section, `key`, `address`, `job`, `targets`; a kit is current while they equal the panel's), `created_by`, `verified_at` and `verified_by` (when a check opened it with its passphrase, and who), `created`, `updated`. Admins read it; only the panel's routes write it; the newest 20 are kept |

Snapshots are not stored; they are listed on demand from the repository through the agent.

The plain table `_pc_panel` (#32), one row that the API and the dashboard do not see and that travels in `data.db` with the panel's backup, holds `key_id` (the id of the master key that sealed the database, which a start with another key is refused by), `ca_pin` (the pin of its internal CA: a database that recorded one never gets a new CA at a start), `restored_at` and `restored_from` (when the panel was last restored from its backup, and the marker `panel recover` left). See [Panel backup and disaster recovery](architecture.md#panel-backup-and-disaster-recovery-32).

## Settings

Panel-wide settings live in a single `settings` record next to PocketBase's own settings (SMTP, S3 for files): `public_url`, `grpc_address`, `audit_retention_days`, `command_queue_ttl_s`, and the SMTP relay of PHP sites' mail (#51): `smtp_host` (empty: mail is off), `smtp_port`, `smtp_tls` (starttls / tls / off), `smtp_user`, `smtp_password` 🔒 (hidden; set through `/api/pc/settings/smtp`), `smtp_password_set`, `smtp_from` (the sender, required with a host), and the integrity checks of backups (#31): `backup_check_schedule` (cron in UTC; empty turns them off; `0 5 * * 0` from the migration) and `backup_check_groups` (how many groups a repository's data packs are read in, one per check; 0 checks the structure only; 20 from the migration), and the restore tests of database backups (#53): `restore_test_schedule` (cron in UTC; empty turns them off; `20 5 * * 3` from the migration). Defaults for renewal join them with their features.
