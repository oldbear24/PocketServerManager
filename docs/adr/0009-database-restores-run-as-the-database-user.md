# ADR 0009: A database's backup goes through the relay, and its restore runs as the database's own user

**Status:** accepted · **Issue:** #53

## Context

A shared database server holds the databases of several applications of one host. Each application has its own database, its own user with privileges on that database only, and its own network to the server. #53 backs up each database on its own, restores one without touching the others (AC1), proves weekly that a backup can be restored (AC2), and keeps the daily backups of a 1 GB database small (AC3). These facts decide how:

- **restic runs only in the agent's job containers**, hardened and given exactly what they need. The agent's image has no database client; the server's own client, of the server's version, is in the server's container.
- **Whoever restores a dump runs what it says.** A plain SQL file can `USE` another database, and a PostgreSQL archive can `RESET ROLE` back to whoever signed in. Restored as the administrator, a crafted or simply wrong dump reaches every database of the server. #29's MySQL dump is `--all-databases`: restored, it rolls back every database there.
- **The server checks a password only over the network.** PostgreSQL's image trusts every role on its local socket; over the container's own address the server asks for the password. The panel keeps each user's password, sealed, for every database of a shared server, those moved in included.
- **restic's chunks are content-defined**, about 1 MiB on average. A dump deduplicates only where its bytes stay the same from one day to the next; an extended INSERT of thousands of rows changes as a whole when one of its rows changes.
- **PostgreSQL renames a database inside a transaction, MariaDB cannot rename one.** A dropped database does not come back on either.

## Decision

- **D1. The dump goes through #29's relay.** restic's `--stdin-from-command` runs `pocketcloud-agent backup-tool relay` in the job container, not the dump. The dump runs with `docker exec` in the shared server's container, with the administrator's password from that container's own environment, so no command carries a database password. The agent writes the dump's output to the relay in frames, and the relay exits with the dump's exit code, so a failed dump saves no snapshot. This deviates from the issue's `--stdin-from-command <dump>`, which needs a client of every server version in the agent's image and the database's network and credentials in the job.
- **D2. The dump is made to deduplicate.** It names one database, never `--databases` or `--all-databases`, so it holds no `CREATE DATABASE` and no `USE`. PostgreSQL's is the custom format, uncompressed (`--compress=0`). MariaDB's goes beyond the issue's flags: `--skip-extended-insert` puts each row on a line of its own, so a changed row changes one line and restic's chunks find the rest again; `--order-by-primary` keeps the rows' order and `--skip-dump-date` the footer; `--no-autocommit` keeps the restore of one-row INSERTs at one transaction per table. Each snapshot is tagged `db:<database>` and `dbserver:<server>` besides `pocketcloud` and `job:<id>`, and the retention selects a job's snapshots by those two alone and keeps them as one group (`--group-by ''`), so a move, which renames the server, leaves no group that is never pruned.
- **D3. A restore runs as the database's own user, over the container's address.** The agent copies the dump out of the snapshot into the server's container through the Engine's archive API, and the server's own client restores it as the database's user (the user whose databases hold it in the panel's records, never one that is only named like it), with the password the panel holds for that user, added to the command only as it is delivered. The client connects to the container's own address, where the server checks that password, not to the socket, where it would not. The user's privileges cover its database only, so a statement of a dump that names another database fails on privileges (MariaDB's client, with `--one-database`, skips what follows a `USE` of another one), and nothing in it can become the administrator. A preview signs in first; a password the server no longer takes refuses a restore in place. A restore test takes the same path, so a passing test proves the restore that would run.
- **D4. On PostgreSQL a restore in place swaps a checked copy in.** The dump goes into a scratch copy `pc_rs_<restore id>`, owned by the user, while the application keeps running, and its tables are counted against the dump's. Only then does the application stop; one transaction renames the database to `pc_old_<restore id>` and the copy to the database's name, and the application starts again. A failure before the swap changes nothing, and the downtime is the stop, the swap and the start. The swap's process runs in the server's container and can commit although it fails afterwards, or although the agent restarts meanwhile: the agent then asks the server whether `pc_old_<restore id>` is there and the copy's name gone, and only without `pc_old_` says that nothing changed.
- **D5. On MariaDB a rehearsal comes first.** The dump goes into a scratch copy as the user while the application runs; the tables are counted and the copy is dropped. Then the application stops, and the database is dropped, made again with its character set and restored; its user's grants survive the drop. The drop comes only when the time left before the command's deadline exceeds the rehearsal's time and a margin, as the restore after it runs to its end while the panel gives up on the command at its deadline. A failure after the drop leaves the application stopped, with its restart policies put back, and raises a critical alert: it never starts on a database that holds part of the backup.
- **D6. The data before a PostgreSQL restore stays 24 hours.** `pc_old_<restore id>` is closed to connections and dropped by the panel 24 hours after the restore, or sooner by an operator. MariaDB keeps no such copy, and the restore drawer says so.
- **D7. Temporary databases are records in a reserved namespace.** Every database PocketCloud makes for a restore or a restore test is named `^pc_(rt|rs|old)_[a-z0-9]{15}$`, after the check or the restore, and is a `databases` record with `temporary_until`, created in the transaction of the command that makes the database. The record is the schedule: across restarts of the panel and the agent, a sweep drops what passed its time. Nobody can give a database such a name, and every statement that drops one checks the name against the namespace, so a drop of a temporary database never reaches an application's. A name of the namespace that a server reports without a record, as after a panel restored from an older backup (#32), becomes a record and is dropped.

## Alternatives

- **Restoring as the administrator** with `SET ROLE` or `pg_restore --role`, as a move restores its dumps (`databases.RestoreFile`): a PostgreSQL archive can `RESET ROLE`, and a MariaDB file can `USE` any database.
- **restic running the dump itself** in the job container: a client of the server's version in the agent's image, and the database's network and credentials in the job. restic in the database's container breaks the rule that restic runs only in job containers.
- **Drop, recreate and restore on PostgreSQL too**: not atomic, and the application stays down for the whole restore.
- **Moving MariaDB's tables out of the way** with `RENAME TABLE` and replaying triggers, views, routines and events: `RENAME TABLE` refuses a table with triggers across schemas, and the replay is fragile.
- **A temporary role with a computed SCRAM verifier** for restore tests: more parts, and it proves less than the database's own user does.
- **A collection of its own for temporary databases**: `databases` has `temporary_until` already, and `db.stats` and the Databáze page show such records already.
- **`db_dump` jobs made by the panel**: four of #29's guards assume a dump has a stack and a service. A source kind of its own leaves them alone.

## Consequences

- AC1 holds by privilege, not by care: a crafted statement on another database fails as denied to the user, MariaDB's client skips what follows a `USE` of another one, and the rehearsal or the scratch copy means nothing changed in place when a restore fails.
- Objects only a superuser can make, such as an untrusted extension or a MariaDB `DEFINER` of another user, cannot be restored as the user. That is the isolation at work: the weekly restore test shows it first, and a restore in place changes nothing.
- A database whose user's password the panel no longer knows, as when an application changed it, cannot be restored in place. A restore into a new database still works.
- A restore in place needs room for a second copy on the server (for 24 hours after, on PostgreSQL): the preview refuses below 1.2 times the larger of the database and the dump, plus 512 MiB.
- MariaDB in place is not atomic. After the drop, a full disk or a crash leaves a partial database and the application stopped until someone restores again; the rehearsal makes it rare.
- Deduplication depends on where the changes are. k row changes scattered over a 1 GB dump touch about 1 − e^(−k/1024) of its 1 MiB chunks, 62 % at k = 1000; restic's compression then bounds the growth. `--skip-extended-insert` makes MariaDB's dumps larger and their restores slower.
- Restore tests load the production server weekly with a full restore and a copy for up to two hours, and read remote targets weekly. One test per server at a time, one temporary copy per server and the space check bound it.
- Temporary records add an audit entry for each create and delete, per database and week.
