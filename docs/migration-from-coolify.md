# Migrating from Coolify

> Status: plan. PocketCloud is in the design phase; this describes how a Coolify installation moves over once the features from M2–M4 exist, and what the importer (milestone [M6](https://github.com/oldbear24/PocketServerManager/milestone/7)) automates. Facts about Coolify refer to **v4.4** (October 2026). Coolify 4.0–4.3 differ in two ways that matter here: container labels use numeric ids (`coolify.applicationId` instead of `coolify.applicationUuid`), and a separate `coolify-realtime` container runs.

## How the two differ

Both run Docker workloads on your servers, put a reverse proxy with automatic certificates in front of them and back up databases. The differences decide how the migration works:

| | Coolify | PocketCloud |
|---|---|---|
| Reaching servers | SSH from the Coolify instance, usually as root | agent container on each server dials out over gRPC + mTLS; no SSH, works behind NAT |
| Building apps | builds images from Git (Nixpacks, Railpack, Dockerfile, Compose) | deploys images and Compose stacks; builds only static and PHP sites |
| Proxy | Traefik (`coolify-proxy`) or caddy-docker-proxy, configured with container labels | Caddy edge container, routes generated by the panel |
| Certificates | Traefik's Let's Encrypt resolver on each server (HTTP-01 by default) | issued centrally by the panel, HTTP-01 or DNS-01, wildcards |
| DNS | you create the records | records created through a connected DNS provider |
| Databases | one container per database resource | shared server per host, one database and user per app (dedicated instances still possible) |
| Configuration store | Coolify's own PostgreSQL (`coolify-db`) | PocketBase inside the panel, every change in the audit log |

## What maps to what

| Coolify | PocketCloud | Notes |
|---|---|---|
| Server | Host with the agent container | install with one `docker run`; Coolify's SSH key can be removed afterwards |
| Project / environment | stack and site names | no projects in PocketCloud; the importer uses `<project>-<resource>` names and keeps the original names as labels |
| Application · Docker Compose | Stack | compose from Coolify, Coolify and Traefik labels removed, domains become `pocketcloud.domain` labels |
| Application · Docker Image | Stack with one service | image, ports, environment, volumes |
| Application · Dockerfile / Nixpacks / Railpack | Stack with an image from CI | PocketCloud does not build app images; build them in CI (e.g. GitHub Actions → GHCR) and let CI trigger the deploy with an API token. Until then the stack can run the last image Coolify built on that server (`<app-uuid>:<commit>`) |
| Application · Static | Static site | Git source, build command, publish directory; Coolify's SPA flag → SPA fallback |
| PHP app (Nixpacks or Dockerfile) | PHP site | when it is WordPress, Laravel or Nette; otherwise a stack |
| Service (one-click template) | Stack | Coolify's generated compose plus the `.env` with all resolved values |
| Database · PostgreSQL, MySQL, MariaDB | Database on a shared server, or a dedicated stack | dump and restore into a shared server, or keep the container and its volume as a dedicated server |
| Database · MongoDB, Redis, KeyDB, Dragonfly, ClickHouse | Dedicated stack | same image and volume |
| Environment variables, shared variables (`{{team.X}}`, `{{project.X}}`, `{{environment.X}}`, `{{server.X}}`) | Stack or site environment, secrets | resolved values are taken over; sensitive ones become encrypted secrets |
| Magic variables (`SERVICE_PASSWORD_*`, `SERVICE_USER_*`, `SERVICE_URL_*`, `SERVICE_FQDN_*` …) | Plain values and secrets | the generated values are copied, never regenerated – passwords already stored in volumes must keep working |
| Domains (`fqdn`, per-service domains) | Domains | `https://app.example.com:3000` in Coolify means container port 3000 → `pocketcloud.port` |
| www / non-www redirect, force HTTPS, basic auth | Domain and site options | custom Traefik labels and middlewares are listed for manual review |
| Persistent storage · volumes | The same named volumes | in place they are reused as `external` volumes – no copy |
| Persistent storage · bind mounts | Bind mounts | same host paths |
| Persistent storage · file mounts | Files in the stack | content from Coolify (stored in its database and under `/data/coolify/applications/<uuid>/`) |
| Scheduled tasks | Scheduled tasks | same model: cron, command, container, timeout; run with `docker exec` |
| Scheduled database backups (S3) | Per-database restic backups | old dumps stay in S3; restic repositories start fresh |
| Volume backups (4.3+) | Backup jobs for volumes | |
| Health checks | Compose `healthcheck` | |
| Preview deployments | – | not supported |
| Git webhooks, GitHub App auto-deploy | CI pipeline + API token; webhook for static and PHP sites | |
| Notifications | Alerts and notification channels | |
| Team members | Users with roles (admin, operator, viewer) | |
| Sentinel metrics | Agent metrics | |

## Two ways to migrate

**A – onto a new server, side by side.** Recommended when you can run a second server for a few days. Nothing on the Coolify server changes until DNS is switched, everything can be tested first, and rolling back means switching DNS back.

**B – in place, on the same server.** Containers are recreated by PocketCloud, but the volumes stay where they are, so no data is copied. Ports 80 and 443 can only belong to one proxy, so the switch from Coolify's Traefik to PocketCloud's edge happens in one maintenance window – usually minutes – with Coolify kept stopped (not deleted) as the way back.

Both can be mixed: move a busy app in place and rebuild the rest on a new server, or migrate one server at a time.

## Preparation

1. **Update Coolify** to 4.3 or newer if possible. Since 4.3 the server export (`GET /api/v1/servers/{uuid}/export`) gives the importer one complete JSON bundle per server. The server Coolify itself runs on (“localhost”) cannot be exported; for it the importer reads the per-resource API and the server itself (see [Importer](#importer)).
2. **API token for the importer.** Settings → Advanced → *API access* on, with the PocketCloud panel's IP in the allowed list. Keys & Tokens → API tokens → permission `read:sensitive` (includes `read`), created by a team admin or owner – otherwise Coolify leaves secrets out of the answers. Values marked “shown once” are never returned by the per-resource API; the export bundle includes them.
3. **Install the PocketCloud panel.** Not on a server whose ports 80/443 Coolify's proxy holds – or there on other ports until the switch. Connect your DNS provider in the panel, so certificates can be issued with DNS-01 before any traffic moves.
4. **Install the agent** on every Coolify server (roles `docker` and `backup`, without `edge` for now). It needs no inbound ports and does not touch Coolify's containers; they show up in PocketCloud's inventory, and backup jobs can already cover their volumes.
5. **Take a backup you can restore without Coolify:** PocketCloud backup jobs for the volumes and database dumps of every resource, plus a copy of `/data/coolify`.
6. **Lower DNS TTLs** to 300 s a day before switching (path A).

## Path A – new server

1. Connect the new server (agent with roles `docker`, `edge`, `backup`) and create a shared database server on it.
2. Run the importer with the new server as the target. It creates stacks, sites, databases, scheduled tasks and backup jobs there – nothing is started yet – and lists what needs manual work.
3. Copy data per app, with the app stopped on the old server for a consistent copy:
   - databases: dump from the Coolify container, restore into the database the importer created on the shared server;
   - volumes: restore the volume backup from the old host into the same-named volume on the new host.
4. Start the app on the new server. Certificates are already there (DNS-01) or are issued right after the DNS switch (HTTP-01).
5. Test through a hosts-file entry or a temporary subdomain.
6. Switch DNS – PocketCloud updates the records if the zone is connected, otherwise change them at the registrar.
7. Keep the old server untouched for a week, then remove Coolify from it.

## Path B – in place

1. Run the importer in *in place* mode. Stacks reuse the existing volumes (`external: true` with Coolify's names such as `<uuid>_postgres-data`), the same images and the same environment values. Nothing is started yet; check the plan and its warnings.
2. Issue the certificates in advance (DNS-01). Without a connected DNS provider they are issued with HTTP-01 right after the switch, a few seconds per domain.
3. Maintenance window – the importer runs these as one command with a progress timeline:
   1. cut Coolify off so it cannot redeploy anything or restart its proxy: on the Coolify host stop the control plane – `coolify`, `coolify-db`, `coolify-redis`, `coolify-sentinel` (and `coolify-realtime` on 4.3 and older); on other servers it manages, stop `coolify-sentinel` and remove Coolify's SSH key from `authorized_keys` (or stop the Coolify instance);
   2. stop the containers labelled `coolify.managed=true` and set their restart policy to `no`, so they stay stopped across reboots;
   3. stop `coolify-proxy`, turn on the `edge` role (starts `pocketcloud-edge` on 80/443);
   4. start the PocketCloud stacks and sites;
   5. check every domain.
4. **Rollback**, if something is wrong: stop the PocketCloud stacks and the edge, start `coolify-proxy`, the app containers and the control plane again (and put the SSH key back). Nothing has been deleted.
5. Later, app by app: move databases from dedicated containers into the shared server (Databáze → *Přesunout na …*), and give Coolify's volume names a cleaner name if you care (that one is a copy).

### Without the importer

Both paths also work by hand with the stack, site, database and backup features. For each resource:

1. take the compose file Coolify generated – `/data/coolify/applications/<uuid>/docker-compose.yaml`, `/data/coolify/services/<uuid>/docker-compose.yml` or `/data/coolify/databases/<uuid>/docker-compose.yml` – and the `.env` next to it;
2. remove the `coolify.*`, `traefik.*` and `caddy_*` labels, add `pocketcloud.domain` and `pocketcloud.port` for every domain, and mark the volumes `external: true` (in place) so the existing data is used;
3. create a stack from it in PocketCloud, put the values from `.env` into its environment and secrets;
4. continue with the data, certificate and switch steps above.

## Things to watch

- **Never delete migrated resources inside Coolify.** After an in-place migration the PocketCloud stacks use Coolify's volumes; deleting the resource in Coolify's UI can delete those volumes. Delete the whole server in Coolify instead (that only removes Coolify's records) or uninstall Coolify as described below.
- **Names inside environment values.** Apps reach other resources by Coolify container names – a database URL looks like `postgres://user:pass@<db-uuid>:5432/db`. The importer finds these references, and either keeps the old name as a network alias or rewrites the value when the database moves to a shared server (new host, user and password).
- **Generated secrets.** Magic variables and database passwords are copied as they are. Regenerating them would lock apps out of data that already exists.
- **Apps built from Git.** Without a CI pipeline they keep running on the last image Coolify built, but nothing updates them. Set up the pipeline before you need the next deploy.
- **Custom proxy configuration.** Traefik labels you added by hand (headers, rate limits, IP allow lists, extra routers) and files in `/data/coolify/proxy/dynamic/` have no automatic equivalent; the importer lists them.
- **Published database ports.** Coolify can publish a database on a public port. Shared servers in PocketCloud never publish ports; keep such a database dedicated or reach it through a VPN or SSH tunnel.
- **Container names change.** Coolify names containers `<uuid>-<timestamp>`; anything outside Coolify that relies on those names (host cron jobs, monitoring) needs updating.

## Removing Coolify

After a week without problems, on each former Coolify host (based on Coolify's own uninstall steps):

```sh
# control plane and proxy
docker rm -f coolify coolify-db coolify-redis coolify-sentinel coolify-proxy
docker rm -f coolify-realtime 2>/dev/null || true      # Coolify 4.3 and older

# old app containers – containers only: without -v their volumes stay,
# and in place (path B) the PocketCloud stacks use them now
docker ps -aq --filter label=coolify.managed=true | xargs -r docker rm

docker volume rm coolify-db coolify-redis
docker network rm coolify
tar czf /root/coolify-data.tgz /data/coolify && rm -rf /data/coolify
```

`docker rm` without `-f` refuses running containers, so anything still running under a Coolify label shows up as an error instead of disappearing. Afterwards remove the Coolify images, the networks Coolify created per resource (named by the resource's uuid) and the key with the comment `coolify` from `~/.ssh/authorized_keys` on every server it managed. Deleting a server inside Coolify does not clean anything up on the server itself.

## Importer

Planned in milestone M6. It works from three sources and prefers the most complete one for each fact:

1. **Server export bundle** (Coolify 4.3+, `read:sensitive`): projects, environments, applications, services, databases, storages, scheduled tasks, backups and environment variables with their values – including “shown once” ones. Can also be uploaded as a file (optionally encrypted with a passphrase by Coolify).
2. **Coolify REST API** for servers that cannot be exported (the Coolify host itself) and for older versions: `/applications`, `/services`, `/databases` with their `/envs`, `/storages`, `/scheduled-tasks` and `/backups`.
3. **The agent on the server**: `docker inspect` of every container labelled `coolify.managed=true` (labels, environment, mounts, networks, images) and Coolify's generated files under `/data/coolify` read through the agent's read-only host mount. This fills in values the API hides and also works when Coolify itself is already broken.

The result is a plan with one row per Coolify resource – target type, target server, database choice (shared or dedicated), warnings – that you review before anything changes. Execution is a parent command with a step per resource, like the new-site wizard, and every object it creates appears in the audit log with the source `import`.
